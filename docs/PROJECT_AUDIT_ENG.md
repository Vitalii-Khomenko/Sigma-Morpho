# Sigma Morpho Project Audit

Date: 2026-04-11

## Scope

This audit covered:

- the local validation workflow based on `test_server.py`
- the automatic archived-run wrapper `scripts/run_sigma_session.sh`
- current build and test health for the Rust project
- the reliability of the previously observed `429` findings

## Executive Summary

The project is currently in a workable state for local validation and research-oriented smoke testing.

- The Rust test suite passes successfully.
- The automatic run wrapper now creates archived run directories in the format `runs/YYYY-MM-DD_HH-MM-SS_HOST_OR_IP_PORT/`.
- The large number of `429` responses in the local smoke runs is valid for the provided test server and is caused by intentional rate limiting in `test_server.py`.
- One wrapper defect was identified during the audit: relative file paths could be resolved incorrectly in some shell edge cases. This was fixed during the audit.

## Validation of the 429 Results

The local verification server implements the following behavior:

- It keeps a 1-second sliding window of request timestamps.
- If more than 5 requests are observed in that window, it returns `429 Rate Limited by WAF!`.
- If the path contains `admin` or `hidden`, it returns `403`.
- If the path contains `api` or `public`, it returns `200`.
- Everything else returns `404`.

Because of that logic, a fast or concurrent run against many `api`-prefixed paths will naturally generate many `429` responses.

### Conclusion on 429 Accuracy

The `429` results are valid for the local test environment.

They are not false positives from Sigma Morpho. They are generated by the synthetic server once the request rate exceeds the configured threshold. The earlier high-volume runs with many `api` paths and higher concurrency therefore correctly produced many `429` findings.

## Findings

### 1. Fixed During Audit: Relative path handling in the wrapper

Severity: Medium

The automatic shell wrapper previously had a path-resolution edge case where a bad relative path could fall back to an unintended location instead of failing clearly.

Impact:

- the wrong wordlist could be used silently
- metadata could record a misleading input file
- archived runs could appear valid while using the wrong dataset

Status:

- fixed during this audit
- relative paths are now resolved from the repository root
- invalid paths now fail explicitly

### 2. Local test server is intentionally synthetic

Severity: Low

The local validation server is useful for smoke testing but not for realistic HTTP behavior benchmarking.

Examples:

- any path containing `api` or `public` returns `200`, even if it would not exist on a real service
- rate limiting is global and simplistic
- response bodies are small and deterministic

Impact:

- the server is good for verifying the adaptive control flow
- it is not suitable for estimating real-world endpoint discovery quality or false-positive rate

### 3. Wrapper coverage is manual, not automated

Severity: Low

The archived-run wrapper is validated manually, but it does not currently have automated shell regression tests.

Impact:

- future shell changes can regress path resolution or artifact creation behavior
- these failures would likely be discovered only during runtime testing

## Recommendations

1. Add a small automated regression test for `scripts/run_sigma_session.sh` that verifies directory naming, artifact creation, and relative path resolution.
2. Consider copying the exact wordlist snapshot into each run directory to make every archived run fully self-contained.
3. If the wrapper is becoming a primary workflow, consider moving the run-archive creation logic into the Rust CLI so behavior is consistent across shell environments.

## Final Assessment

Sigma Morpho is currently healthy enough for local experimentation and archived smoke testing.

The previously observed `429` responses are correct for the provided local server. The main issue uncovered during this audit was operational rather than algorithmic: the shell wrapper needed stricter path handling. That issue has now been corrected.
